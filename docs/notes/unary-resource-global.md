# The unary resource as one FD propagator — parked as too specific, shape recorded

- **status**: parked design (Aug 2026) — the human's call: the engine
  is generic and this is a scheduling-domain global; recorded so the
  shape survives, not scheduled. Superseding context: the scheduling
  benchmark's losing pole is a UNIT-DURATION degenerate instance (the
  porter's imposition, not the 2021 formulation) — a faithful
  instrument for this store would use varied durations.
- **evidence held**: the benchmark verdict (pairwise clauses lose the
  no-external-knowledge pole) plus the standard CP argument: group
  infeasibility is a SUM over k tasks and cannot factor through
  pairwise constraints — three 2-hour tasks in a 5-hour stretch fail
  as a triple while every pair fits.
- **imports**: ⋯import the disjunctive / unary resource constraint
  (constraint-based scheduling's global; its internal shorthands —
  est/lct, edge-finding, energetic reasoning — deliberately NOT
  entering the ring) — receipt owed if built.
- **obligations** (if ever built): none live. The recorded shape:
  1. ONE FD-toolkit Propagator, pldb's GAC table constraint being the
     shipped precedent for a set-watching propagator: storeClass =
     FiniteDomainConstraints, name = "resource", watchedTerms = all
     starts (and variable durations), transcription free via the
     named-schema rebuild.
  2. Door: one static method taking the (start, duration) list,
     activating with a doom check = the add-up-and-compare test at
     pricing (pure domain reads).
  3. Body: the existing Verdict/Update contract — fail on group
     overload (total need exceeds the group's stretch), narrow starts
     that provably cannot run before a full group ("someone must go
     last"), keep otherwise; DomainUpdate's equal-domain guard makes
     the wake loop safe as for addo.
  4. Its one own law, capability-ladder style: pruning soundness —
     every removed value belongs to no feasible schedule — checkable
     against a brute-force small-instance oracle; the generic
     imposition laws (kit stage 2) already cover the rest.
  5. Open: variable durations reason with minima (under-counting never
     over-prunes); task sets are fixed at posting — dynamic accrual
     (tabling replay composing resources) would need same-name merge
     at the store, undesigned.
